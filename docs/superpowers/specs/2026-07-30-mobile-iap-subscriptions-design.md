# Mobile In-App Purchase Subscriptions — Design

**Date:** 2026-07-30
**Status:** Approved (design); pending implementation plan
**Related:** #1104 (paid-tier enforcement, blocked on billing), #1115 (finish Stripe billing), the feature-flag entitlement system (`packages/shared/src/feature-flags.ts`)

## Goal

Let riders subscribe to the `pro` (€29.99/yr) and `premium` (€49.99/yr) tiers from the mobile app via **Apple StoreKit** and **Google Play Billing**, feeding the **same** `users.subscription_tier` the Stripe web flow already drives — so the existing feature-flag entitlement resolver is unchanged. One active subscription per rider at a time (across Stripe / Apple / Google), with a 14-day intro trial granted once per rider.

## Decisions (locked)

- **Platforms:** iOS **and** Android, designed together, delivered in phases.
- **Trial:** mirror the web flow — a **14-day intro free trial**, granted **once per rider**, gated by `users.billing_trial_used_at` across _all_ sources (web + both stores).
- **Cross-platform:** **one active subscription at a time.** A store purchase is blocked while a Stripe subscription is active, and vice-versa. The tier comes from the single active source.
- **Data model:** **Approach A — extend `users`** (denormalized), not a separate `subscriptions` table. Correct under the single-active constraint and needs no `feature-resolver` change.
- **Validation:** server-side only. Apple = StoreKit 2 signed transactions + App Store Server API + App Store Server Notifications v2. Google = Play Developer API token validation + Real-Time Developer Notifications. The client never grants a tier.

## Architecture

### Data model (migration on `users`)

New nullable columns:

- `subscription_provider` `varchar(16)` — `stripe | apple | google`; **`null` means "no owned subscription" (a TERMINAL state), NOT merely "tier is currently free."** The discriminator for who owns the subscription slot. **It is retained through a TEMPORARY access loss** — a Google account hold / Play pause (or an Apple billing-retry-without-grace) drops the _tier_ to `free` but keeps `subscription_provider` set, because the provider still owns the slot and the subscription can recover. Clearing the provider whenever the tier goes free would release the slot mid-interruption, letting Stripe or Apple claim it, so the eventual `SUBSCRIPTION_RECOVERED` / renewal would then conflict after Google resumes charging. The provider is cleared to `null` ONLY on a genuinely terminal transition (`EXPIRED`/`REVOKED`/`REFUND`, an ordinary Stripe end) — the same identity-guarded terminal writes described below.
- `apple_original_transaction_id` `varchar(255)` — Apple's stable per-subscription key; used to find the rider from an ASSN v2 notification.
- `google_purchase_token` `varchar(1024)` — Google's purchase token; used to find the rider from an RTDN and to re-query the Play Developer API.

**A store subscription belongs to exactly one rider.** Both store-id columns get a **UNIQUE partial index** (`WHERE <col> IS NOT NULL`) so the same transaction/token can never be claimed by two accounts (which would duplicate the entitlement and make notification lookup ambiguous). Purchases are additionally **bound to the account at purchase time** via the stores' account-linking identifiers — Apple `appAccountToken` (a UUID the client sets to a value the backend maps to the rider) and Google `obfuscatedExternalAccountId` — so mere possession of a valid transaction/token can't reassign a subscription to a different signed-in account: `iap/validate` rejects (409) a store payload whose account-linking id doesn't map to the authenticated rider, and rejects a store id already owned by another rider.

Backfill: `subscription_provider = 'stripe'` where `stripe_subscription_id IS NOT NULL`, else `NULL`.

**New table `processed_store_notifications`** (transactional inbox for notification dedupe): `(provider, notification_id)` with a UNIQUE constraint, a `status` (`pending` | `completed` | **`dead_letter`** — the terminal state the sweeper moves an unrecoverable poison row to; the enum / check-constraint MUST include it or the transition fails and poison rows stay `pending` with their payloads), a **lease** (`locked_by`, `lease_expires_at`), a **`payload` JSONB carrying the processing context** — the verified store identifiers needed to re-query without a fresh delivery (Google: the purchase token; Apple: the `originalTransactionId` / the signed notification body; the resolved `user_id`) — and **dedicated audit/retry columns kept OUTSIDE the payload so they survive redaction: `event_type`, `attempts`, `max_attempts`/`first_seen_at` (retry-budget inputs), `failure_class` (`transient`/`permanent`), `dead_letter_reason` (`permanent_reject`/`corrupt_context` — set when dead-lettered; decides whether a later redelivery re-opens the row), `last_error`, `created_at`, `updated_at`, `dead_lettered_at`.** (`event_type` in particular must be its own column, not only inside `payload`, so dead-lettering can null the sensitive JSON while retaining the auditable failure record + the retry-budget accounting.) The row is persisted BEFORE any external side effect and marked `completed` after. A conflict on a `completed` row is skipped as a true duplicate; a conflict on a `pending` row is RESUMED under the lease (reclaimable only when unheld or expired), so a worker that crashes after claiming but before completing doesn't strand the notification — **but if the stored payload is UNDECODABLE, resume does not blindly re-read the corrupt context: a verified fresh delivery REPAIRS the `pending` row in place** (signature + `bundleId`/environment re-checked on the delivered body, then the stored payload is replaced with the fresh one and reprocessing continues). This must happen at the `pending` stage, NOT only after dead-letter — the row reaches `dead_letter` only after the bounded retry budget, by which time the store's redelivery window may already be exhausted, so waiting would lose the refund/revoke/renewal. (Recovery from a corrupt stored payload is thus available in BOTH states: repair-in-place while `pending`, re-open while `dead_letter` with `corrupt_context`.) **a conflict on a `dead_letter` row is handled by the DEAD-LETTER REASON** (`dead_letter_reason`), because the two dead-letter classes recover differently: a **permanent-rejection / intrinsically-invalid** dead letter (`permanent_reject` — the store will never accept the operation, or the signed data itself was invalid) is a **terminal SKIP** — the webhook is acknowledged (200), NOT reprocessed and NOT resumed from the nulled payload (it must not re-fail the endpoint forever or read redacted context). But a **corrupt-stored-context** dead letter (`corrupt_context` — the row was dead-lettered because its STORED payload was undecodable due to a serialization/storage bug or a since-fixed defect, NOT because the event was intrinsically bad) is **RECOVERABLE from a fresh redelivery**: a store redelivery with the same notification id carries intact signed data and may be the only remaining chance to apply the refund/revoke/renewal (a distinct follow-up notification is NOT guaranteed). So a **verified** fresh redelivery (signature + `bundleId`/environment re-checked on the delivered body, not the redacted stored one) **re-opens the `corrupt_context` dead letter** — reset to `pending` with the freshly-delivered payload and reprocess — while `permanent_reject` stays a terminal skip. (Requires the sweeper to record which class it dead-lettered as; only `corrupt_context` unlocks re-open.) Because the payload is stored, a **sweeper can reclaim an expired-lease `pending` row and finish it even with NO store redelivery** (the raw message id alone would give neither the purchase token nor the signed body, so it could not re-query — the persisted context is what makes sweeper recovery possible). **Retention: the `payload` (purchase tokens, resolved `user_id`, Apple's signed body) is processing context, not a permanent record — on `completed` it is NULLed, so a completed row keeps only the dedupe key + status. Every renewal inserts a row, so the table would otherwise grow unbounded and retain sensitive billing context indefinitely; a bounded cleanup / partition-retention job keeps rows only for the stores' redelivery horizon (Apple/Pub/Sub retry window, ~a few days) and prunes older completed rows. A row that can NEVER complete needs a terminal policy, but **redaction is gated on the FAILURE CLASSIFICATION, because destroying the payload also destroys the only means of re-query** (the notification id alone can't re-query): - **Permanent poison** (the store PERMANENTLY rejects the operation — a 4xx that won't change — `dead_letter_reason = permanent_reject`; OR the stored context is undecodable — `dead_letter_reason = corrupt_context`): after the bounded retry budget the sweeper moves the row to `dead_letter`, **REDACTS the payload** (nulls token/signed body/user_id), keeps an **auditable failure record** (notification id, provider, event type, last error, attempt count, timestamps, `dead_letter_reason`), stops retrying, and alerts ops. A `permanent_reject` effect is genuinely unrecoverable so nothing is lost by redacting; a `corrupt_context` row is redacted too (its STORED copy was bad), but a later **verified fresh redelivery of the same notification id RE-OPENS it** from the intact delivered data (see the conflict rule above) — the redaction removes only the corrupt stored copy, not the recovery path. - **Transient-blocked** (a VALID notification failing only because the store API or DB is DOWN — 5xx/timeout/connection): this MUST stay recoverable. It is NOT redacted while the failure looks transient — the sweeper keeps retrying with backoff and **escalates to ops for manual replay if the outage outlasts the budget**, RETAINING the payload so the renewal/revoke/refund can still be applied once the dependency recovers. Redacting a transient-blocked event would silently drop a real billing transition. (Distinguish by the error class the retry loop already sees; only a permanent classification unlocks redaction.)
This keeps poison rows size-bounded and stripped of sensitive data WITHOUT discarding a recoverable event during a prolonged outage.** See Error handling.

**New table `store_billing_reconciliations`** (durable work items for charges that need human/async follow-up — the inbox cannot represent these, because a terminal rejection at `iap/validate` is NOT a notification and an Apple sub with no server-cancel API stays open across many future events). Columns: `id`, `user_id`, `provider`, store id (`apple_original_transaction_id` / `google_purchase_token`), `reason` (`ineligible_trial_rejected` | `exclusivity_conflict` | `deletion_cancel_failed` | …), `status` (`open` | `resolved`), `resolution` (`rider_canceled` | `refunded` | `expired` | `server_canceled` | …), `detail` JSONB, `created_at`, `resolved_at`. A row is opened whenever a charge **the authenticated rider owns** is granted-no-entitlement or otherwise needs closing out (Apple terminal rejection, a losing exclusivity claim, a Google deletion-time server-cancel that failed and is retained for retry) — and `user_id`/store id are always the OWNER's, taken from the verified account-linking id, never the submitter's when they differ.

- **An account-binding / ownership failure is explicitly NOT a reconciliation reason and MUST NOT create an actionable row.** The store id in that case belongs to a DIFFERENT rider; associating it with the caller and letting the queue processor drain it would let an attacker who submits a victim's token drive a refund/revoke/close-out of the victim's legitimate purchase — exactly what the validate ownership rule (409, mutates nothing) forbids. An ownership failure is handled entirely by the 409 (no DB mutation on the victim's subscription); at most it may write a **security/audit log keyed to the SUBMITTER** (not a reconciliation work item, never carrying the victim's store id as an actionable target). The processor only ever drains rows whose store id belongs to that row's `user_id`.

It is closed when a later ASSN v2 / RTDN event — or an admin/ops action — observes the store subscription cancelled/expired/refunded. This is the persistent counterpart to the "retained reconciliation entry" the terminal-rejection and exclusivity flows reference, and it is what a retry/queue processor drains.

**New table `store_billing_emails`** (per-email delivery ledger/outbox, created by the FIRST delivery phase that sends a notification-triggered transactional email — P1, the Apple ASSN v2 handler). Columns: **`(provider, notification_id, template)` UNIQUE** — `provider` is included to match the inbox's composite identity `(provider, notification_id)`, so Apple and Google can never collide on a shared identifier (the second provider's email misread as the first's existing delivery) and each ledger row correlates unambiguously with its composite-key inbox row; `status` (`pending`/`sent`), `provider_message_id`, `created_at`, `sent_at`. A row is written `pending` before the send and marked `sent` after, so a resumed inbox retry can consult it; combined with the ESP-side idempotency key / status lookup (see Error handling) it makes a notification email exactly-once. **Retention is tied to its inbox row's LIFETIME, not the redelivery horizon:** an email-ledger row is kept as long as its `processed_store_notifications` row is non-terminal (a transient-blocked inbox row can stay recoverable and be manually replayed long after the store's redelivery window), because pruning the ledger while a replay is still possible — after the ESP's own idempotency/status record has also expired — would let the replay re-send the email with no record to dedupe against. It is pruned only once its inbox row reaches a terminal state (`completed`/`dead_letter`) AND its own retention window has elapsed. If a phase adds a notification-triggered email, it owns this table's migration + tests.

`feature-resolver` is **unchanged** — it reads `user.subscription_tier`; all three sources converge on that field plus `subscription_status`, `subscription_current_period_end`, `subscription_cancel_at_period_end`.

### Shared (`@tarmoto/shared`)

- `SUBSCRIPTION_PROVIDERS = ['stripe','apple','google'] as const` + `SubscriptionProvider` type.
- `IAP_PRODUCTS`: the tier ↔ store-product map, single-sourced so mobile and backend agree. **Because StoreKit auto-applies whichever introductory offer is configured on an Apple product — the client can't opt a given Apple product out of its trial — each tier maps to TWO Apple products, one with the intro trial and one without.** Google expresses this with one product + a trial base-plan/offer and a no-trial base-plan. So:
  `{ pro: { apple: { trial: 'com.tarmoto.pro.annual.trial', noTrial: 'com.tarmoto.pro.annual' }, google: { productId: 'pro_annual', trialOffer: '…', noTrialBasePlan: '…' } }, premium: {…} }`.
  Both Apple products (and both Google base-plans) map to the same tier server-side, so tier derivation is unaffected; the _offer selection_ is what trial-eligibility drives.
- Request/response DTO types for the validate endpoint.

### Backend (`apps/backend/src/modules/account`, or a new `billing/iap` submodule)

**`AppleBillingClient`**

- Verify a StoreKit 2 signed `JWSTransaction` against Apple's public keys (x5c chain → Apple root). **A valid signature only proves Apple issued the transaction — NOT that it belongs to this app or environment.** So after signature verification, also assert the decoded payload's **`bundleId` equals `TARMOTO_APPLE_IAP_BUNDLE_ID`** and its **environment (`Sandbox`/`Production`) equals `TARMOTO_APPLE_IAP_ENVIRONMENT`**; reject on either mismatch BEFORE the product/account-token mapping runs. Without these checks a genuine, Apple-signed transaction issued for a different app (or a sandbox transaction replayed against production) could reach tier derivation and grant a Tarmoto entitlement.
- Query the App Store Server API (`GET /inApps/v1/subscriptions/{originalTransactionId}`) with an ES256 JWT (issuer id + key id + `.p8`).
- Decode + verify ASSN v2 notification payloads (signed JWS) — and apply the **same `bundleId` + environment identity checks** to the decoded notification data before acting on it, so a notification for another app/environment can't drive a tier change.
- Env: `TARMOTO_APPLE_IAP_ISSUER_ID`, `TARMOTO_APPLE_IAP_KEY_ID`, `TARMOTO_APPLE_IAP_PRIVATE_KEY` (`.p8`), `TARMOTO_APPLE_IAP_BUNDLE_ID`, `TARMOTO_APPLE_IAP_ENVIRONMENT` (sandbox|production).

**`GoogleBillingClient`**

- Validate a purchase token via the Play Developer API (`purchases.subscriptionsv2.get`) with a service-account JWT.
- Decode RTDN messages (Pub/Sub push envelope → `SubscriptionNotification`).
- Acknowledge the purchase server-side if not auto-acked — but **only AFTER the purchase is classified non-terminal and an entitlement is granted (or a backend refund/revoke has completed)**, NEVER as an unconditional step of token verification. Acknowledging is not part of `get`/verify: it must sit downstream of account-binding, trial-eligibility, and exclusivity classification. Acknowledging a purchase the backend then terminally rejects would disable Play's automatic-refund safety net (Play auto-refunds an _unacknowledged_ purchase within its window) and leave the rider charged with no entitlement — contradicting the Android close-out rules below. So `GoogleBillingClient` exposes verify and acknowledge as SEPARATE operations, and the `iap/validate` flow calls acknowledge only on the grant path. **Because the entitlement commits before the acknowledge call, acknowledgement is tracked as durable state (an `acknowledged` flag / pending-ack marker) and is retried** — on the next re-validate of that purchase and by a background sweeper — so a grant whose acknowledge timed out or was interrupted still gets acknowledged before Play's auto-refund window elapses (acknowledging is idempotent, so a retry after a partial success is safe).
- Env: `TARMOTO_GOOGLE_IAP_SERVICE_ACCOUNT_JSON` (or path), `TARMOTO_GOOGLE_IAP_PACKAGE_NAME`, `TARMOTO_GOOGLE_IAP_PUBSUB_VERIFICATION_TOKEN`.

**Endpoints**

- `POST /account/subscription/iap/validate` — authed. Body `{ provider: 'apple'|'google', transaction | purchaseToken }`. (Any client `productId` is a hint only — never trusted for entitlement.)
  1. Verify with the store client (signature + Apple `bundleId`/environment identity check + server API).
  2. **Account binding FIRST — before any product/tier classification or terminal close-out.** Reject (409) when the verified payload's account-linking id (Apple `appAccountToken` / Google `obfuscatedExternalAccountId`) doesn't map to the authenticated rider, or when the store id is already owned by another rider (unique-index conflict → 409). This 409 **mutates nothing** — no refund, no revoke, no acknowledge. Ownership MUST be established before the unknown-product / hint-mismatch rejections below, otherwise a token belonging to another rider could enter a terminal close-out (Android refund/revoke) and cancel the victim's legitimate purchase (see the Android close-out rule).
  3. **Derive the tier from the VERIFIED payload's product / base-plan id** (returned by Apple/Google), mapped through `IAP_PRODUCTS` — never from a client-supplied field. Reject an unknown product; reject when a client `productId` hint disagrees with the verified one (a client claiming Premium for a verified Pro purchase must fail, not escalate). Because binding already passed, any terminal close-out here acts only on the authenticated rider's OWN purchase.
  4. **Exclusivity (atomic claim):** claim the provider slot atomically (see below); 409 if a DIFFERENT provider is already active. **Same-provider is NOT automatically safe:** if the rider already has an active store subscription of the same provider and this is a DIFFERENT token/product (e.g. an Android Pro holder submits a separate Premium token), do not silently overwrite the stored id — that would leave the first product renewing and unaddressable by RTDN. Require it to be the store's in-place replacement (Play subscription-replacement / Apple upgrade within the same subscription group, which keeps one `original_transaction_id`); otherwise reject (409) and cancel/refund-reconcile the duplicate. Only replace the stored token when the store confirms the old one is superseded.
  5. Set `subscription_tier/status/current_period_end/cancel_at_period_end`, `subscription_provider`, and the store id column — all from the verified payload. Also set `plan_source = 'subscription'` (matching the Stripe handler) so a launch-granted `founder` who now pays through a store is no longer labelled a founder in the admin UI.
  6. **Trial:** honour a trial only when the rider is backend-eligible (`billing_trial_used_at IS NULL`). Since `billing_trial_used_at` can't control a store's offer, the client queries backend eligibility _before_ purchase and buys the **no-trial Apple product / no-trial Google base-plan** (see `IAP_PRODUCTS`) for ineligible riders; if a trial transaction still arrives for an ineligible rider the backend **rejects and reconciles it** (no second trial). On a genuine first trial, stamp `billing_trial_used_at`.
  7. Return the same subscription snapshot shape as `GET /account/subscription`.
     Idempotent on the store transaction id, but **NOT a blind no-op: a re-validate must reconcile any still-pending Google acknowledgement**. Track acknowledgement as durable state (an `acknowledged` flag on the subscription row / a pending-ack marker), because the grant commits BEFORE the Play `acknowledge` call and that call can time out or the worker can crash after the commit. If it does, the client sees a retryable failure and revalidates — and if this path simply returned the snapshot, the purchase would stay UNACKNOWLEDGED until Play auto-refunds it even though Tarmoto recorded an active entitlement. So on a re-validate of an already-granted-but-unacknowledged Google purchase, **retry the acknowledge** (idempotent — acknowledging twice is safe) before returning the snapshot; a background sweeper also re-acknowledges any granted-but-unacknowledged rows so a client that never revalidates is still covered.
     **Rider lookup + terminal semantics (both stores).** A handler resolves the rider by the store id **OR** the verified account-linking id (`appAccountToken` / `obfuscatedExternalAccountId`), and a terminal transition **retains the store binding** (the store-id column stays as a historical binding) while clearing only the ACTIVE ownership (`subscription_provider = null`, tier → `free`, `plan_source` cleared). This is what lets a store-side reactivation (renew re-enabled, or resubscribe in store settings while the app is closed) still find the rider and re-claim — see the reactivation events below. **All access decisions come from the re-queried store entitlement state, never the event name alone.**
     **Every terminal write is CONDITIONAL on the event's subscription identity still being the rider's active one** — a guarded `UPDATE … WHERE subscription_provider = :eventProvider AND <store-id column> = :eventStoreId`. Resolving the rider by the account-linking id is necessary (a reactivation must find them) but is NOT sufficient authority to clear their tier: a delayed terminal event for an OLD token (the rider already replaced it with a new Apple/Google subscription that re-queries as active) resolves the same rider, and an unconditional clear would wipe their NEW valid provider/tier. The identity guard makes such a stale terminal a no-op — it only clears when the terminating subscription is the one currently stored as active. (The reconciliation record for the old token, if any, still closes on its own store id.)

- `POST /account/subscription/iap/apple/notifications` — ASSN v2 (JWS-verified, no user auth). Lifecycle: `SUBSCRIBED` (resubscribe/reactivate → re-validate + re-claim), `DID_RENEW`, `DID_FAIL_TO_RENEW` (→ `past_due`; tier held ONLY during a real billing-grace window per the payload dates), `DID_RECOVER` (→ `active`; recovery need not emit `DID_RENEW`), `GRACE_PERIOD_EXPIRED` (grace exhausted → drop the TIER to `free`, but **retain `subscription_provider`** — Apple's billing retry can still recover (`DID_RECOVER`) for up to ~60 days, so this is a temporary loss, not the terminal `EXPIRED`; the slot stays owned until an actual terminal event), `DID_CHANGE_RENEWAL_PREF` (a Pro↔Premium change WITHIN the Apple subscription group — the validation design explicitly permits in-place Apple upgrades, so the group product can change without a new `original_transaction_id`; **re-query the transaction and re-derive the tier from the VERIFIED renewal product**, then sync. Honour Apple's timing: an **upgrade** takes effect immediately (raise the tier now), a **downgrade** takes effect at the next renewal (Apple keeps the higher product billed until the period ends, so keep the current higher tier and record the pending lower product — the later `DID_RENEW` carries the downgraded product and flips the tier). Never trust the event to name the product; only the re-queried verified product decides the tier — otherwise an immediate upgrade can leave a paying Premium rider on Pro, or a downgrade can strip Premium before its effective date), `DID_CHANGE_RENEWAL_STATUS` (carries an **auto-renew ON/OFF subtype** — handle both: **OFF** while still paid → **keep tier + set `cancel_at_period_end = true`; do NOT terminal-clear** — access continues until the paid period actually ends; **ON** (the rider re-enabled auto-renew before the period expired) → **re-query and CLEAR `cancel_at_period_end`** so a subscription that will in fact renew is no longer marked as ending. Without the ON branch the flag stays stale-true after a disable-then-reenable, mis-showing the plan as canceling), `EXPIRED` (period ended → terminal), `REFUND`/`REVOKE` (terminal).
- `POST /account/subscription/iap/google/notifications` — RTDN via authenticated Pub/Sub push → re-query the Play Developer API → sync: `SUBSCRIPTION_PURCHASED` (activate a deferred/pending purchase — bind a _pending_ token to the rider at `validate` time so a purchase completing while the app is closed isn't free-after-charge), `SUBSCRIPTION_RENEWED`, `SUBSCRIPTION_RESTARTED` (reactivate → re-claim), `SUBSCRIPTION_IN_GRACE_PERIOD` (hold — still has access), `SUBSCRIPTION_ON_HOLD` (account hold has NO access → drop the TIER to `free` **but RETAIN `subscription_provider` — this is a temporary loss, not terminal**, so the slot isn't released for another provider to claim mid-hold; restore on recovery), `SUBSCRIPTION_PAUSED` (Play's pause feature — the rider has NO access for the paused period → re-query Play and drop the tier to `free`, **again retaining the provider**; restore on `SUBSCRIPTION_RESTARTED`), `SUBSCRIPTION_RECOVERED`, `SUBSCRIPTION_CANCELED` (**renewal disabled but still entitled until the re-queried expiry → keep tier + token, set `cancel_at_period_end`; clear only after the state actually expires**), `SUBSCRIPTION_EXPIRED`/`SUBSCRIPTION_REVOKED` (terminal).
- `GET /account/subscription` extended: add `provider`, `managed_by` (`stripe_portal | app_store | play_store`), and trial-eligibility. **The snapshot must be gated by `subscription_provider`, not merely annotated:** `getSubscription`/`buildSubscriptionSnapshot` today load live Stripe whenever `stripe_customer_id` exists and prefer that plan — for a store subscriber (who may still have an old canceled Stripe customer) that returns a stale Stripe tier/status/payment-method/invoices. So query + overlay Stripe billing ONLY when `subscription_provider === 'stripe'`; for a store provider build the snapshot from the stored `subscription_*` fields (no Stripe read), and omit Stripe-only fields (payment method, invoices) or source them from the store where available.

**Exclusivity enforcement (atomic provider claim, every activation path)**

Blocking only the two synchronous entry points is insufficient: a Stripe Checkout session created earlier can complete _after_ a store purchase, and an expired store subscription can be reactivated from store settings _after_ Stripe becomes active — those webhook/notification paths would then silently overwrite the shared fields while both providers keep billing. So exclusivity is an **atomic provider claim** applied on **every** activation:

- Model the claim as a conditional write: a provider may set the active-subscription fields only when `subscription_provider IS NULL` or already equals that provider (a single guarded `UPDATE … WHERE subscription_provider IS NULL OR subscription_provider = :provider`, run inside the request/notification transaction, is the claim).
- **Guard same-provider by subscription IDENTITY, not just the provider name — including Stripe.** A free rider can open two Stripe Checkout sessions before completing either; both later webhooks share `provider = 'stripe'` and would pass a provider-only claim, letting the second activation overwrite the stored `stripe_subscription_id` while BOTH subscriptions keep billing. So the claim also rejects an activation whose subscription/token id differs from the one already stored for that provider (unless it's the store/Stripe in-place replacement of the same subscription); the loser is cancelled + reconciled. This mirrors the same-store-token rule and applies equally to Stripe, Apple, and Google.
- **Entry points:** `createCheckoutSession` (Stripe) 403s when a store provider is active/trialing/past_due (reusing the "Existing subscriptions must be changed in the billing portal" guard, store-specific copy); `iap/validate` 409s when Stripe (or the other store) is active.
- **Async paths:** the Stripe webhook and both store notification handlers run the same guarded claim. On a **conflict** (a different subscription id already owns the slot — cross-provider OR same-provider), they do NOT overwrite — they log a reconciliation event for support and undo the losing charge, not merely stop future billing: **Stripe cancels the losing subscription AND refunds/voids its already-paid initial invoice** (two concurrent Checkout sessions can each pay a full annual invoice before the claim detects the duplicate; cancellation alone leaves the rider charged twice), **Google refunds+revokes** the duplicate via the Play Developer API, and **Apple** flags it for the rider's refund flow (no server refund API). The paid-two-session race is covered in the webhook tests.
- **Release the claim on terminal transitions.** The claim is only correct if it's RELEASED when a provider's subscription ends. The existing Stripe deletion/expiry branch (`handleSubscriptionUpdated(..., true)`) currently clears only the Stripe id + tier; P0 must also make it clear `subscription_provider` (and `plan_source`), otherwise after an ordinary Stripe expiration the row stays owned by `stripe` and every later Apple/Google `validate` conflicts even though the rider is free. Covered in the webhook/migration tests. (The store notification terminal branch already clears the provider — keep both symmetric.)
- **Guard the Stripe terminal clear by subscription IDENTITY — same rule as the store terminal writes.** `handleSubscriptionUpdated` today resolves the rider by Stripe customer / metadata and clears the tier + Stripe id **without comparing `subscription.id`**. Stripe redelivers events, and a customer can hold a newer subscription on the same customer id after an old one ended, so a **retried old `customer.subscription.deleted` for a superseded subscription would clear the rider's NEWER active subscription/tier**. P0 must make the terminal clear conditional: a guarded `UPDATE … WHERE subscription_provider = 'stripe' AND stripe_subscription_id = :eventSubscriptionId`, so a terminal event for a subscription that is no longer the stored active one is a no-op. This mirrors the store-side identity-guarded terminal rule (both stores AND Stripe). Covered in the webhook tests (a stale `subscription.deleted` after a newer subscription is active does not clear it).

**Account deletion**

- **Provider-split cancellation, run at REQUEST time — not at purge, and REVERSIBLE.** `AccountDeletionService` locks login immediately on the deletion request but hard-purges only after the 30-day grace, and it explicitly treats those 30 days as a **support restoration window**. Two things must both hold: a still-active subscription must not renew-and-charge during the grace, AND a rider restored within the window must get their subscription back intact. An **immediate hard cancel** (`stripe.subscriptions.cancel` / `purchases.subscriptionsv2.cancel`) satisfies the first but violates the second — a restored rider would have an irreversibly-canceled annual sub and lose the remaining paid period. So the request-time cancellation must use the **reversible, period-end form**:
  - **Stripe:** set **`cancel_at_period_end = true`** at the acknowledged deletion request (NOT `subscriptions.cancel`), which stops the next renewal (no mid-grace charge) while leaving the current paid period intact; **on restoration within the window, clear `cancel_at_period_end`** to reinstate it. Today the Stripe cancel runs in `purgeUser` only AFTER `deletion_scheduled_at <= now` (`account-deletion.service.ts:349-370`) — P0 moves a `cancel_at_period_end` set to request time (failures retained for retry) and adds the restoration reversal.
  - **Reversal is only possible while the subscription is still live.** `cancel_at_period_end` takes effect at the period boundary, so if the rider's **renewal date falls inside the 30-day window and they are restored AFTER it**, Stripe has already ended the subscription — clearing the flag can no longer revive it (and an analogous Google token may have expired). So the restoration guarantee is **conditional on the current period not having ended**: a restore before the period boundary reinstates in place; a restore after it (the subscription lapsed during the grace) **requires the rider to re-subscribe** — the restoration UI/copy states this, and it is a defined, tested path, not an unconditional "we'll bring it back."
  - **Google:** `purchases.subscriptionsv2.cancel` stops future renewal without clawing back the current paid period — and it MUST use the **`USER_REQUESTED_STOP_RENEWALS`** cancellation type (which leaves the subscription restorable by the rider in Play), NOT the developer-requested stop-payments mode (which the rider cannot restore). Even so, Play exposes **no server-side inverse** to re-enable a cancelled renewal, and re-validating the still-live token only confirms the REMAINING entitlement, it does not un-cancel. So Google reversal is NOT server-side automatic (unlike Stripe): an in-window restoration keeps the rider on their remaining paid period, but to keep the subscription BEYOND it the **rider must re-enable renewal in the Play subscription center (or re-subscribe)** — the restoration copy/email says so explicitly. If they don't, it lapses at expiry (no charge — the intended outcome for an abandoned deletion). Google therefore behaves like Apple for reversal (rider action required), not like Stripe.
  - **Apple has no server-cancel API** — only Apple's manage-subscriptions surface can cancel — so App Store subscriptions keep the rider-must-cancel guidance, surfaced before the account locks. (An Apple rider who cancels and then restores must re-subscribe; call that out in the restoration copy.)
- **Warn (and act) BEFORE the mutating delete.** The companion currently calls `deleteAccount` only after the confirm dialog and immediately signs out (`settings/data/page.tsx`), so a fact returned by `DELETE /account` arrives only after the account is already soft-deleted — too late to drive a pre-delete warning, and after the hard purge even the store-token association needed for follow-up notifications is gone. So the store-management state must come from a **preflight** (`GET /account/subscription`, already store-provider-gated) shown in the confirm dialog, **or** the first `DELETE` is made **non-mutating** until an explicit store-cancellation acknowledgement is submitted. For an Apple-managed sub the confirmation UI + email prominently instruct the rider to cancel in the App Store before proceeding; for **Google AND Stripe** the backend stops the next renewal server-side **during the acknowledged deletion request** using the **period-end form** (Stripe `cancel_at_period_end = true`, Google deferred cancel — never an immediate hard cancel, which would forfeit a restored rider's remaining paid period; never at the later purge — login locks immediately, so deferring would let a renewal charge land in the 30-day grace window), retaining failures for retry. **On restoration the reversal is provider-specific: the backend clears Stripe's `cancel_at_period_end` (a true server-side reverse); Google has NO server-side inverse, so the rider must re-enable renewal in Play / re-subscribe** (see the per-provider bullets above) — the restoration copy states which applies.

### Mobile (`apps/mobile`, `react-native-iap`)

- **`services/iap.ts`** — connect on demand; fetch products (localized store prices); purchase; transaction/purchase listener; **finish (iOS) / acknowledge (Android) only after** the backend validate succeeds; restore purchases; teardown.
- **Paywall sheet** — pro/premium with store-localized prices + trial copy + purchase/restore. Reads product metadata from `react-native-iap`.
- Wire the ~10 `UpgradePrompt` `onUpgrade` call sites (MapScreen, RideDetailScreen, TripsScreen, GroupRideScreen, TripCreateScreen, OfflineRegionsScreen, CommuteScreen, TripDetailScreen, SettingsScreen) → open the paywall.
- Purchase flow: buy → `POST /account/subscription/iap/validate` → refresh `/users/me` entitlements → finish/acknowledge the transaction. On backend failure, branch on the error kind rather than a blanket "don't finish": a **retryable** outage (5xx / network) leaves the transaction unfinished so the store re-delivers and a later validate succeeds. A **terminal** rejection (wrong `appAccountToken`, unknown product, ineligible-trial, exclusivity conflict) can never validate — but the two stores differ on how to close it out safely:
  - **iOS:** `finishTransaction` alone is NOT sufficient to close out a terminal rejection — it only removes the transaction from StoreKit's unfinished queue; it does **not** disable auto-renewal. An ineligible-trial (or otherwise rejected) Apple subscription that is merely finished will still **renew and charge** the rider on the next period even though the backend granted no entitlement. Apple exposes no server-side cancel/refund API, so the client must (a) `finishTransaction`, (b) prominently direct the rider to **cancel the subscription** in the App Store's manage-subscriptions surface (not just the one-off refund-request flow — cancellation is what stops the recurring charge), and (c) the backend opens a durable **`store_billing_reconciliations`** row (`reason: 'ineligible_trial_rejected'`, `status: 'open'`) — persisted at `iap/validate` rejection time, NOT in the notification inbox (a rejection is not a notification) — that stays open until a later ASSN v2 event or a re-query observes the subscription cancelled/expired/refunded, at which point the processor marks it `resolved`. Support/ops can see and chase still-`open` rows if the rider never cancels. The rejected subscription is not considered closed out until that cancellation/refund is confirmed.
  - **Android:** **do NOT `acknowledge`** — Play auto-refunds an _unacknowledged_ purchase within its window, whereas `acknowledge` (or `cancel`, which only stops future renewal) would leave the rider charged with no entitlement. So on a terminal Android rejection **that belongs to the authenticated rider** the backend refunds/revokes via the Play Developer API and only THEN acknowledges, or the client leaves it unacknowledged so Play auto-refunds. Never acknowledge a rejected Android purchase.
    - **CRITICAL exception — never refund/revoke a purchase bound to ANOTHER rider.** An ownership failure (the verified `obfuscatedExternalAccountId` maps to a different rider, or the token is already owned by another account) is a **409 that mutates NOTHING** — no refund, no revoke, no acknowledge. Refund/revoke is reserved for purchases PROVEN to belong to the authenticated caller. Otherwise anyone who obtained a victim's valid purchase token could submit it under their own account and have the backend cancel the victim's legitimate subscription. So the Android close-out order is: verify → **account-binding check first** (mismatch → 409, no mutation) → only for own-purchase terminal rejections (ineligible-trial, unknown product, self-exclusivity) does the refund/revoke path run.
      The validate endpoint returns a machine-readable `retryable: boolean` + provider so the client drives the right close-out.
- **Restore purchases** in Settings → re-validate the current entitlement.
- **Status display** — show the plan + a "Manage in App Store / Play Store" deep link (store subs are managed in the store, not in-app).
- **Trial eligibility — backend eligibility is necessary but NOT sufficient to ADVERTISE a trial.** `billing_trial_used_at IS NULL` only means _Tarmoto_ hasn't granted this rider a trial; the rider's **Apple ID / Google account may have already consumed the store's introductory offer**, in which case StoreKit won't apply the intro price and Play may omit the trial offer entirely. Advertising "14-day free trial" off backend eligibility alone would then charge the full annual Apple price (or fail the Android purchase). So the paywall must **combine backend eligibility WITH store-side eligibility**: on iOS check StoreKit subscription-group introductory-offer eligibility (`Product.SubscriptionInfo.isEligibleForIntroOffer` / the eligibility API); on Android read the **offers actually returned** by the Play Billing query (only advertise the trial if the trial base-plan/offer is present). Advertise (and select the trial product) only when BOTH the backend AND the store report the rider eligible; otherwise show — and buy — the no-trial product. (See the validate `Trial` step, which remains the server-side backstop: an ineligible-rider trial transaction is still rejected + reconciled.)

## Data flows

- **Purchase:** mobile buy → store → transaction → mobile → `iap/validate` → backend verifies with store API → sets tier → snapshot → mobile refreshes entitlements + finishes transaction.
- **Renewal / cancel / refund / grace:** store → ASSN v2 / RTDN → backend notification handler → re-query store → sync tier/status/period_end. A cancel-before-expiry keeps the tier only until the re-queried expiry actually passes. (A retry-without-grace regression test asserts access is dropped, not held — see the testing strategy.)
- **Restore:** mobile restore → `iap/validate` with the restored transaction → same as purchase.
- **Exclusivity:** a store purchase attempt via `iap/validate` while another source is active → **backend 409** (the status the validate contract and the atomic-claim section specify — NOT 403) → the mobile client branches on 409 to show "manage your existing subscription first." ## Error handling & correctness

- Server validation is the only source of a grant; the client is never trusted.
- Idempotent `validate` (transaction-id dedupe) + **durable notification dedupe**: a `processed_store_notifications` table with a UNIQUE key on the notification id (Apple `notificationUUID` / Google Pub/Sub message id) acting as a transactional inbox. **A unique-conflict is NOT unconditionally skipped — the row's `status` decides**: a conflict on a `completed` row is a true duplicate and is skipped; a conflict on a `pending` row means a prior attempt claimed it but did not finish (a worker committed the `pending` row then crashed before completion), so a redelivery must **RESUME** it, not drop it forever. To make that safe under concurrency the `pending` claim is a **lease**: the row carries a `locked_by` / `lease_expires_at`, and a redelivery may reclaim the row only when no lease is held or the lease has expired (a compare-and-set that excludes a still-active worker); a live lease means another worker is mid-flight, so this delivery defers (Pub/Sub redelivers, ASSN retries). A sweeper/queue processor also reclaims `pending` rows whose lease has expired so a crash without redelivery still gets finished. Re-querying makes the DB **field** updates idempotent on their own; the one-shot **external** side effects (emails, cancellations, refunds) need this lease + the pending-first outbox below.
- **External side effects must be replay-safe, not merely transaction-scoped.** A single DB transaction cannot atomically span a store API call or an email send: if the external effect succeeds but a later DB op in the same transaction fails, the transaction (and the inbox INSERT with it) rolls back, and the retried notification re-runs the irreversible effect (double-refund, double-cancel, duplicate email). So the inbox row is a **two-phase pending→completed record, persisted BEFORE the external call**:
  1. In its own committed step, INSERT the inbox row `pending` with a lease (`locked_by` = this worker, `lease_expires_at`) **and the `payload` re-query context** (purchase token / `originalTransactionId` / signed body, resolved `user_id`, event type) — this claims the notification against concurrent/duplicate delivery, durably records intent before any side effect runs, AND lets the sweeper finish a stranded row without a fresh store delivery. A redelivery that finds an existing `pending` row reclaims it only if the lease is unheld/expired (else it defers to the live worker).
  2. Make each external effect safe to re-issue — but **by the mechanism the specific receiver actually supports, not a uniform "attach an idempotency key" assumption**:
     - **Stripe:** a real `Idempotency-Key` header derived from the notification id (Stripe honours it) — key-based dedup.
     - **Google Play:** the `purchases.subscriptionsv2.cancel`/`refund`/`revoke` APIs do **NOT** accept an arbitrary idempotency key carrying the notification id, so key-based dedup is not available. Recovery is **re-query-then-act**, but a bare pre-check is NOT enough on its own — a first mutation that timed out or exceeded its lease may still be **in flight or accepted-but-not-yet-visible**, so a reclaimed worker that re-queries could observe the OLD state and re-issue, running the operation twice. So the recovery is hardened three ways: (1) **the lease must exceed the operation's worst-case execution + Play's visibility lag**, so a reclaim can't legitimately overlap a still-running first attempt; (2) **each operation's own "already-applied" semantics are used** — `cancel` is naturally idempotent (cancelling an already-cancelled/expired sub is a no-op), and `refund`/`revoke` return a detectable already-refunded/already-revoked error that the handler treats as SUCCESS, not a retry; (3) for the genuinely-ambiguous window, the handler **polls the subscription's terminal state (bounded) for the operation to become visible before deciding to re-issue**, and only issues when Play still shows the pre-operation state after the poll. A regression test covers an in-flight / accepted-but-unobserved first call (the second attempt must NOT double-apply).
     - **Apple:** no server refund/cancel API at all — the "operation" is a reconciliation record + rider guidance, deduped by the `store_billing_reconciliations` row keyed on `notificationUUID`/store id, and closed by a later re-query/ASSN event.
       **Email is no exception, and a local delivery-ledger ALONE cannot make it exactly-once** — because between "the ESP accepted the message" and "the ledger row is marked sent" there is a window where a recovered `pending` ledger row is indistinguishable from one that crashed _before_ sending: resending duplicates, skipping can lose the mail. The authoritative dedup must therefore live at the RECEIVER: the email send MUST use an **ESP-supported idempotency key or delivery-status lookup** keyed deterministically on `(provider, notification_id, template)` (provider included to match the inbox + ledger composite identity) — the ESP either dedupes the retried send itself (a bare `Message-Id` only works if the chosen ESP explicitly deduplicates on it — not a given), or exposes a status query the resume consults to learn whether that key was already accepted. The `store_billing_emails` ledger/outbox row (written pending-before-send, marked sent-after) is a complement that narrows the window and records intent, not a substitute for receiver-side idempotency. A transactional email whose ESP supports neither idempotency nor a status lookup is not allowed on the inbox-retry path.
  3. Record completion **separately** (mark the inbox row `completed` / mark the email-ledger row sent / store the effect's result) so a resumed retry sees the prior step already done and skips it.
     A retry therefore resumes from the pending record and, for every external effect (store operation AND email), either finds it already completed via its own ledger/key or re-issues it under the same idempotency key the receiver dedupes — never runs it twice. The pure field-sync updates may still commit in one transaction; only the external effects require this pending-first outbox discipline.
- Deferred/pending Google purchases handled (no grant until the token resolves to a purchased state).
- Signature/verification failures reject; a store-API outage during `validate` returns a retryable 5xx (the client can re-validate; the store re-delivers).

NOT a hard cancel) so a Stripe subscriber isn't charged mid-grace yet keeps a restorable subscription; **and the reconciliation retry worker/job that drains `store_billing_reconciliations` (with `deletion_cancel_failed` coverage) MUST ship in P0 too** — since a P0 deployment is independently shippable and already locks the rider out at request time, a failed request-time cancel with no P0 worker to retry it would let the exact mid-grace renewal charge this change prevents still land. **The worker must be restoration-safe, and a bare pre-check is a TOCTOU race** — restoration could commit AFTER the worker reads `deletion_scheduled_at` but BEFORE its external Stripe/Play call, and for Google that cancellation has no server-side inverse. So the worker and the restoration path are **SERIALIZED under a per-rider lock** (a `pg_advisory_xact_lock` on the user id, or a `SELECT … FOR UPDATE` on the user row): the worker takes the lock, re-checks `deletion_scheduled_at` is still set, performs the external cancel, and marks the reconciliation — all under the lock; restoration takes the SAME lock to clear `deletion_scheduled_at` and resolve any open `deletion_cancel_failed` row. Under the lock the two can't interleave — restoration either wins the lock first (so the worker's re-check then sees the deletion cleared and closes the row without cancelling) or waits until the worker finishes. A stale retry can therefore never cancel a restored, now-active subscription.\*\* (P1 reuses the same processor for the Apple terminal-rejection flow.)
- **P1** — Apple: `AppleBillingClient` (verify + **`bundleId`/environment identity checks** + derive tier from verified product + `appAccountToken` binding), `iap/validate` (Apple path), ASSN v2 webhook with the atomic claim + inbox dedupe + conflict reconciliation + grace-vs-hold access rules + `SUBSCRIBED` reactivation + `DID_CHANGE_RENEWAL_PREF` product-change, Stripe/Apple exclusivity, trial-eligibility offer selection (**backend eligibility AND StoreKit intro-offer eligibility**), terminal-vs-retryable validate result, the **Apple reconciliation flow on the P0 `store_billing_reconciliations` table + its open/resolve processor** (opened on a terminal ineligible-trial rejection, closed when a later ASSN v2 event or re-query confirms cancel/expire/refund), and — because the ASSN v2 handler is the first to send a notification-triggered transactional email — the **`store_billing_emails` ledger table + migration + bounded-retention prune + tests**, tests.
- **P2** — Google: `GoogleBillingClient` (`obfuscatedExternalAccountId` binding + pending-purchase token binding), `iap/validate` (Google path) with **acknowledge on the grant path + a durable `acknowledged`/pending-ack marker retried on re-validate and by a sweeper** (a grant whose acknowledge failed after commit still gets acknowledged before Play's auto-refund window), RTDN webhook with the atomic claim + inbox dedupe + `SUBSCRIPTION_ON_HOLD`/`_PAUSED` access drop **(tier→free, provider retained)** + `SUBSCRIPTION_PURCHASED`/`_RESTARTED` activation + cancel-before-expiry, same-provider second-token rejection (refund+revoke), **re-query-based replay recovery for Play operations** (cancel/refund/revoke are made idempotent by re-querying Play's current state on resume, NOT by an idempotency key Play doesn't accept), **deferred cancellation at deletion-request time** (stop next renewal without forfeiting the paid period; **reversal is rider-action, not server-side — Play has no un-cancel API, so restoration keeps the remaining period and the copy tells the rider to re-enable in Play / re-subscribe to keep it beyond expiry**), exclusivity across all three, tests.
- **P3** — mobile: `services/iap.ts`, paywall (trial vs no-trial offer by eligibility — **advertise the trial only when backend eligibility AND the store's own eligibility agree**: StoreKit intro-offer eligibility on iOS, the offers actually returned by Play on Android), wire `UpgradePrompt` CTAs, restore, status display, tests.
- **P4** — ops config + sandbox E2E verification.

Each phase is independently shippable behind the store config being absent (endpoints 503 until env is set, exactly like Stripe today).

**Every phase that changes an HTTP contract regenerates the OpenAPI artifacts in the same PR** (`pnpm openapi:gen` → committed `packages/openapi/openapi.yaml` + `packages/openapi-client/src/generated/schema.d.ts`), so generated consumers see `provider`/`managed_by`/trial-eligibility and the new `iap/validate` + notification routes: P0 (snapshot fields), P1/P2 (new endpoints). Postman regen where a new endpoint lands.

## Ops prerequisites (account owner)

- **App Store Connect:** **4** auto-renewable subscriptions — a trial and a no-trial product **per tier** (pro/premium annual, €29.99/€49.99), because StoreKit auto-applies a product's configured intro offer and can't be told to skip it; the 14-day intro free trial is configured only on the two `*.trial` products. Plus ASSN v2 URL, App Store Server API key (issuer id + key id + `.p8`), bundle id.
- **Google Play Console:** 2 subscription products (pro/premium annual) each with a **14-day free-trial base-plan/offer AND a no-trial base-plan**, a Pub/Sub topic for RTDN, a service account with Play Developer API access, package name.
- Set the `TARMOTO_APPLE_IAP_*` / `TARMOTO_GOOGLE_IAP_*` env vars in the backend deploy.

## Risks / open items

- **Price parity:** store prices are set per-store in local currency; keep them aligned to the €29.99/€49.99 intent (stores don't take an arbitrary amount — pick the closest store price tier). Displayed price comes from the store, not our config.
- **Store review:** the paywall must follow each store's subscription-disclosure rules (price, period, trial terms, restore button, links to terms/privacy).
- **`react-native-iap` native setup:** bare RN 0.85 — pods (iOS) + Play Billing lib (Android); a native dependency addition.
- **Refund/chargeback:** handled via notifications → revoke tier; no separate flow.
