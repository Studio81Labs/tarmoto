# Internationalization (companion)

The companion app (`apps/companion`) renders every user-facing string through a
small in-house translation module rather than a third-party library. The
infrastructure lives under `apps/companion/src/i18n/`. English is the only
locale registered today; this document explains how to add another one and how
the runtime resolves the active locale.

## Architecture

```
apps/companion/src/i18n/
├── index.ts                # Public API: `t`, `translate`, `resolveLocale`, ...
├── I18nProvider.tsx        # React provider + `useI18n` / `useTranslation` hooks
├── server.ts               # Server-side locale resolution (cookie + Accept-Language)
└── locales/
    ├── index.ts            # Registry — add new languages here
    └── en.ts               # English catalog (source of truth for keys)
```

The registry in `src/i18n/locales/index.ts` is the only file that needs to be
edited when adding a language. Everything else (locale switcher, server-side
resolution, html `lang` attribute, fallback to English for missing keys) picks
up the new entry automatically.

## How locale resolution works

1. **Server-side** — `apps/companion/src/i18n/server.ts` reads the
   `tarmoto-locale` cookie first, then the `Accept-Language` header, then
   falls back to `DEFAULT_LOCALE`. The result is passed to
   `<html lang="…">` and to `I18nProvider` so the initial paint already
   uses the right catalog.
2. **Client-side** — `LocaleSwitcher` (in `src/components/LocaleSwitcher.tsx`)
   posts to `/api/locale` to set the cookie, then reloads the page so the
   server re-resolves the locale.
3. **Catalog lookup** — `translate(key)` looks the key up in the active
   locale's catalog. If it's missing, it falls back to the English catalog,
   then to the key itself (so the UI never renders `undefined`).

## Adding a new language

Worked example: adding Estonian (`et`).

1. **Create the catalog file** `apps/companion/src/i18n/locales/et.ts`:

   ```ts
   import type { TranslationCatalog } from ".";

   export const et: Partial<TranslationCatalog> = {
     Home: "Avaleht",
     Trips: "Reisid",
     "Road Explorer": "Teede uurija",
     // …
   };
   ```

   The catalog only needs the keys you actually want to translate. Missing
   keys fall back to English at runtime, so it's safe to ship an
   incomplete catalog and grow it over time.

2. **Register the locale** in `apps/companion/src/i18n/locales/index.ts`:

   ```ts
   import { en, type EnglishMessageKey } from "./en";
   import { et } from "./et";

   export const LOCALES = {
     en: { label: "English", messages: en },
     et: { label: "Eesti", messages: et },
   } as const satisfies Record<string, LocaleEntry>;
   ```

3. **Done.** The locale switcher in `Settings → Language` now lists the new
   language. There are no other places to update.

## Authoring guidelines for translatable strings

- Use the source English text as the translation key, matching the existing
  pattern in `en.ts`. This means `t("Save changes")` is both the call site
  and the key. Translators see legible keys instead of synthetic IDs.
- Pass interpolation values as a record:
  `t("{name}'s profile photo", { name: rider.displayName })`. The `{name}`
  placeholder syntax is the only templating supported — no nested
  expressions, no plural forms (yet).
- When you add a new key to a component, also add it to `en.ts` (with the
  English text as both key and value) so translators have a single source
  of truth for what needs to be translated. Missing keys still render the
  English text, but only because the lookup falls back to the key itself;
  keeping `en.ts` exhaustive keeps the catalog discoverable.
- Avoid concatenating translated fragments
  (`t("Open ") + tripName + t(" in planner")`). Use a single key with a
  placeholder: `t("Open {name} in planner", { name: tripName })`.

## Server vs. client translation

`translate` / `t` work in both server and client components — the module
holds the active locale in module-level state which `I18nProvider` sets on
every render. Server components can also import `t` directly; the locale
is set during the root layout before any children render. Inside React
components prefer `useI18n()` / `useTranslation()` to make the locale
dependency explicit and to benefit from re-renders when the rider
switches language without a full reload.
