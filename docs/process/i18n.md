# Internationalization

Tarmoto shares one i18n core across surfaces: the language registry,
locale resolution, and the ICU translation engine live in
`packages/shared/src/i18n.ts`. Each surface owns its own message catalog
and builds a translator over it with `makeTranslator`:

- **Companion UI** — catalogs in `apps/companion/src/i18n/locales/`,
  translator + React bindings in `apps/companion/src/i18n/`.
- **Mobile UI** — catalog in `apps/mobile/src/i18n/locales/`, translator +
  React bindings in `apps/mobile/src/i18n/`. `I18nProvider` resolves the
  signed-in rider's `users.language` value at the app root.
- **Backend email** — catalog in `apps/backend/src/modules/email/i18n/`,
  translator `translateEmail`. Recipient locale resolves from
  `users.language`.

English is the only registered locale today. The UI copy standard is
British English ("kilometres", "colour", "Motorways").

## The engine

`makeTranslator(catalogs)` looks a key up active-locale → English → the
raw key itself (companion keys ARE the English source text), then formats
with ICU MessageFormat (`intl-messageformat`):

- `{name}` placeholders, `{count, plural, one {# ride} other {# rides}}`,
  `{x, select, a {...} other {...}}`; `#` inside a plural renders the
  count.
- Plural rules follow the locale of the catalog that supplied the
  template — an English fallback string always pluralizes with English
  rules.
- Number glyphs and grouping inside ICU plural `#` and explicit
  `{value, number}` placeholders follow the independently resolved display
  locale (`preferences.format_locale`). UI language still owns the words and
  plural branch. Finite numbers passed to plain `{value}` placeholders are
  localized without grouping, so identifiers such as years are not grouped
  accidentally; string identifiers such as card suffixes remain byte-for-byte
  unchanged.
- Calls WITHOUT values return the template verbatim (no ICU parsing).
- A message that fails to parse or format degrades to the legacy
  `{placeholder}` substitution instead of throwing.
- Markup like `<strong>` is literal text (`ignoreTag`).
- Parsed messages are memoized module-wide (capped, cleared wholesale).

Pinned dependency note: `intl-messageformat` stays on the dual
CJS+ESM `^10.7` line until the workspace goes ESM (v11 is ESM-only and
breaks the backend CJS build).

## Authoring rules (companion)

- The English source text is the key: `t("Save changes")`. Register every
  key in the per-domain module it is used from, under
  `apps/companion/src/i18n/locales/en/` (`common.ts`, `trips.ts`, `map.ts`,
  …), merged by `locales/en/index.ts` (key === value, alphabetical within
  the module; shared keys go in `common.ts`).
  `src/i18n/locales/catalog.test.ts` enforces that every entry parses as ICU
  and avoids `'{`, `'}`, `''`, and `locales/en/duplicate-keys.test.ts`
  enforces that no key lives in two modules.
- `t()` / `translate()` take a **registered catalog key** (`EnglishMessageKey`)
  — an unregistered string is a compile error. For a genuinely dynamic key (a
  runtime string with no fixed key set), use `tDynamic(key)` from `@/i18n`, the
  single loose-typed, greppable escape hatch. Prefer typing a label map
  (`Record<K, EnglishMessageKey>` / `satisfies`) over `tDynamic`.
- Raw user-facing text on `label` / `title` / `alt` / `placeholder` /
  `aria-label` / `ariaLabel` JSX props is flagged by ESLint
  (`no-restricted-syntax` in `apps/companion/eslint.config.mjs`) — the typed
  `t()` check can't see a string that never reaches `t()`. Wrap it
  (`label={t("…")}`); a deliberately non-translatable value (a brand token, a
  dynamic backend string) carries a
  `// eslint-disable-next-line no-restricted-syntax -- <reason>`. It is a
  safety net for the common case, not a proof: it flags only text starting
  with an ASCII letter (so numbers, units, symbols, and empty values pass
  without false positives), across plain literals, template literals with
  static text, and conditional branches at any nesting. It does NOT catch a
  raw string starting with a digit, punctuation, or a non-ASCII letter
  (`"3 stars"`, `"Česky"`, `"…"`). Directly rendered stable wire properties
  (`status`, `surface`, `severity`, `tier`, and `role`) are also rejected;
  map them through a typed `satisfies Record<K, EnglishMessageKey>` table and
  call `t()` at render time. Raw copy assigned to common display locals such
  as `title`, `*Label`, `displayName`, `fallbackName`, and `rideName` is
  rejected too. The typed `t()` check and code review remain the backstop for
  dynamic computed values the lint cannot classify safely.
- Display helpers whose names end in `Label`, `Message`, `Copy`, `Text`,
  `Title`, `Description`, `Unit`, or `Short` are also guarded. They must call
  `t()` themselves or return a typed `EnglishMessageKey`; assembling prose in
  a helper and interpolating the result later is still a catalog bypass.
- Rider-facing error state is catalog copy too. The companion lint guard covers
  direct error/message/banner setters, nested `{ message }` state objects, and
  `onError()` callbacks; translate before crossing those boundaries.
- Plurals: one ICU message per site — never `word{s}` hacks, `=== 1`
  ternaries, or split singular/plural keys. The selection argument is
  named `count` and every message has an `other` branch.
- Numbers a rider sees follow `preferences.format_locale`, NOT the UI
  language (see `docs/superpowers/specs/2026-07-16-companion-locale-formatting-design.md`).
  ICU numeric placeholders and plural `#` are formatted with that locale by
  the shared translator, while plural selection continues to use the UI
  catalog locale. Explicit `format.integer()`/`format.decimal()` calls remain
  appropriate for numbers rendered outside a catalog message.
- Relative-time labels use the shared `formatRelativeTimeLabel()` helper:
  wording comes from the UI catalog and count digits from the format locale.
  Do not render `Formatters.relativeTime()` directly in UI; its words follow
  the format locale and can diverge from the selected UI language.
- Visible fixed-precision values (including coordinates) use
  `format.decimal(value, digits)`. ESLint rejects `toFixed()` inside JSX;
  numeric rounding for geometry, cache keys, and export protocols may still
  use `toFixed()` because those values are not display copy.
- Durations use the shared `Formatters.duration()` / `durationCompact()`
  methods. Active timers use `durationClock()` for locale-aware `m:ss` /
  `h:mm:ss` output. These format numerals and, where present, hour/minute unit
  tokens through `Intl.NumberFormat`; do not assemble raw duration strings.
- Currency uses `Formatters.currency()` / `formatCurrencyAmount()`. API
  contracts carry the numeric minor-unit amount and ISO currency code;
  preformatted backend labels are compatibility data, not display input.
- Subscription responses expose `tier` as the display-content identifier.
  Clients derive plan names, features, descriptions, highlighting, and price
  labels from that tier; the backend does not send English plan prose.
- Curated region records keep operational names for backend matching, but
  companion display names/descriptions use typed English-source catalog keys.
  Riding seasons are numeric month ranges formatted through `Formatters.month()`.
- No concatenated fragments — one key with placeholders.
- Companion pure helpers take a translator as their LAST parameter, typed
  `Translate` (from `@/i18n`), mirroring the `Formatters` threading
  convention. Shared helpers reused by mobile/backend (e.g. `formatJoinedLabel`)
  keep the looser `LooseTranslate` (`@tarmoto/shared`); companion callers pass
  `tDynamic` into those.

## How the companion resolves the locale

1. Server: `apps/companion/src/i18n/server.ts` reads the `tarmoto-locale`
   cookie, then the authenticated account language, then `Accept-Language`,
   then `DEFAULT_LOCALE`; the root layout applies it to `<html lang>` and
   `I18nProvider`. OAuth registration forwards the callback request locale as
   `Accept-Language`, so users created before their first authenticated render
   receive the same browser-detected default as password registrations.
2. Client: `LocaleSwitcher` POSTs `/api/locale` (which also PATCHes
   `users.language` for signed-in riders) and reloads. The switcher stays
   hidden while only one locale is registered. An explicit selection also
   sets `tarmoto-locale-sync-pending`; the route clears that marker only after
   the account PATCH succeeds. `PreferencesSync` therefore sends
   cookie → account only for a pending browser choice, retries transient
   failures with capped backoff, and otherwise lets a newer account/mobile
   language refresh the ordinary browser cookie. A stale locale cookie alone
   never overwrites the account.
3. Lookup: missing keys fall back to English, then to the key text.

## Mobile authoring and locale resolution

- Mobile follows the same English-source-key, ICU plural, typed-key, and
  `tDynamic()` escape-hatch rules as companion. Register copy in
  `apps/mobile/src/i18n/locales/en.ts`; `translate()` / `t()` only accept an
  `EnglishMessageKey`.
- Wrap user-visible React Native copy, accessibility labels, alerts,
  permission rationales, notifications, and vehicle-display copy. The mobile
  ESLint configuration guards common raw JSX/prop/alert/state-message paths
  plus indirect display locals (`title`, `*Label`, `displayName`,
  `fallbackName`, and `rideName`); the catalog type catches unregistered
  translator calls.
- Label maps store `EnglishMessageKey` values and translate at render or call
  time. Do not translate a module-level constant eagerly: that freezes the
  value in the locale active during module initialisation.
- `apps/mobile/App.tsx` passes the authenticated rider's language to
  `I18nProvider`, falling back to the native device locale while signed out.
  The API client also sends that device tag as `Accept-Language`, so a new
  account starts with the correct supported language. `resolveLocale()`
  normalises it and falls back to English; the provider updates both hooks and
  the synchronous translator used by non-React services such as notifications
  and CarPlay/Android Auto.
- Mobile Settings contains the same registry-driven language selector as the
  companion. It remains hidden while only English is registered and persists
  a later choice to `users.language` through the typed profile API.
- Badge DTOs carry stable badge keys, never English names/descriptions.
  Challenge DTOs likewise carry a constrained `content_key`. Each client maps
  those identifiers to typed catalog copy; adding a badge or challenge
  template therefore requires catalog entries in both surfaces.
- Raw NestJS exception messages are diagnostic data. The API facades map HTTP
  status to cataloged rider-facing copy and retain the response body only for
  branching/logging. UI code must never render `ApiError.body.message`.
- `FormatProvider` resolves regional number/date formatting and display
  timezone from the current device first; the account fields only mirror that
  device for backend/server use and are a last-resort fallback when native
  detection is unavailable. Unit system remains account-owned. React screens
  use `useFormat()` and pure/native helpers use the synchronous
  `getFormatters()` seam. Providers publish the latter only after React
  commits, so an abandoned render cannot leak uncommitted preferences to
  notifications or vehicle surfaces, then synchronously re-render descendants
  so legacy render paths using that seam cannot stay on the previous locale or
  units. ESLint rejects direct display
  `toLocale*`/`Intl` construction outside that seam.
- Spoken turn-by-turn phrases remain in `services/navigation.ts`: voice
  navigation has its own `VoiceNavLanguage` preference and must not silently
  follow the UI language.
- Run `pnpm --filter @tarmoto/mobile lint`, `typecheck`, and `test`. The mobile
  catalog tests validate ICU syntax, plural structure, locale completeness,
  key/value identity, and pseudo-catalog expansion.
- Never render or store a caught runtime `Error.message` directly. API errors
  carry the `localizedUserMessage` marker after their message passes through
  the active catalog; use `getUserFacingErrorMessage(error, t("…"))` (or the
  mobile `translate` equivalent) at UI boundaries. Unknown browser, native,
  socket, timeout, and library errors deliberately use the translated
  contextual fallback. ESLint guards error setters, alerts, and toast/message
  properties against regressions.

## Adding a language (checklist)

Worked example: Czech (`cs`).

1. Create catalog modules
   `apps/companion/src/i18n/locales/cs.ts` and the equivalent mobile catalog
   under `apps/mobile/src/i18n/locales/cs.ts`. The engine supports partial
   catalogs while translation is in progress, but keep them unregistered:
   production catalog tests require every English source key before a locale
   can be exposed by either selector.
2. Register it in `companionCatalogs`
   (`apps/companion/src/i18n/locales/index.ts`) and `mobileCatalogs`
   (`apps/mobile/src/i18n/locales/index.ts`).
3. Add the mobile native resources before registering the locale:
   - iOS: add `apps/mobile/ios/TarmotoApp/cs.lproj/InfoPlist.strings` with
     every permission-usage key from the English table, then add the locale
     to the `InfoPlist.strings` variant group in the Xcode project.
   - Android: add `values-cs/strings.xml` for App Actions labels and
     `values-cs/arrays.xml` for localized Assistant hazard phrases. Locale
     tags with a region use the Android BCP-47 directory form, for example
     `pt-BR` → `values-b+pt+BR`.
     The native manifest tests iterate `SUPPORTED_LOCALES`, so registration
     fails until both platforms are complete.
4. Add `cs: { label: "Čeština" }` to `LOCALES` in
   `packages/shared/src/i18n.ts`. This single edit:
   - un-hides the companion and mobile Settings → Language switchers (they
     render only when more than one locale is registered),
   - activates `<html lang>`, the `/api/locale` bridge, and
     `users.language` validation for `cs`,
   - makes the backend trip-copy catalog exhaustive; add the localized
     fallback title, copy label, and template to `TRIP_COPY_MESSAGES` in
     `apps/backend/src/modules/trips/trips.service.ts`,
   - makes backend email resolve `cs` recipients — email catalogs fall
     back to English key-by-key until translated, so no email work is
     required up front.
5. Run the guards: the companion and mobile catalog-completeness tests
   (`src/i18n/index.test.ts` in each app) now require the `cs` entries from
   step 2.
   Companion and mobile ICU-parse/apostrophe/plural checks automatically
   iterate every registered catalog, and their coverage checks reject missing
   or extra source keys. The Czech-shaped engine tests in
   `packages/shared/src/i18n.spec.ts` already prove one/few/other plural
   handling.
6. Translate: work through the per-domain English modules under
   `apps/companion/src/i18n/locales/en/` — plural messages must be rewritten
   with the target language's plural branches, not word-for-word. A new
   locale may be a single `Record<EnglishMessageKey, string>` file
   (`locales/<locale>.ts`) or mirror the English domain split. Fallback remains
   available during development, but all keys are required at registration.

## Server vs. client translation

The companion has no mutable module-level locale. `translate` / `t` from
`@/i18n` are pure functions whose optional locale argument defaults to English;
they are suitable for locale-independent code and tests, not as an implicit
request or browser locale.

- Client components call `useI18n()` / `useTranslation()` from
  `@/i18n/I18nProvider`. The provider binds the translator to the locale that
  the root layout resolved for this render, and context updates re-render
  consumers after a language change. ESLint rejects client-component imports
  of `t`, `translate`, or `tDynamic` from `@/i18n`.
- Client helpers outside React receive a `Translate` argument from their
  component boundary. Browser-only infrastructure that cannot practically
  receive one (the generated API error adapter) reads the root layout's
  resolved `<html lang>` with `getDocumentLocale()` and passes that locale
  explicitly to the pure translator.
- Server components import `t` from `@/i18n/server` (not `@/i18n`). It defaults
  to `getServerLocale()`, the per-request ref, so a concurrent request cannot
  affect translation before or across a Suspense boundary.

### Strict per-request isolation on the server

`readLocale()` stores the resolved locale in a `React.cache()`-backed ref
(read via `getServerLocale()`) so it is scoped per request/render pass. An
awaiting server component therefore keeps the locale selected for its own
request; import the request-bound translator:

```ts
import { t } from "@/i18n/server";

export default async function MyServerPage() {
  await something();
  return <h1>{t("Home")}</h1>;
}
```

`t` from `@/i18n/server` already defaults its locale to `getServerLocale()`
— no manual threading needed. Reach for `getServerLocale()` directly only
when a _non-`t`-importing_ helper or child component needs the raw locale
value itself (e.g. to pass on as a typed prop) rather than to call `t()`.

The root layout awaits `readLocale()` before returning JSX, but server modules
still use the request-bound import consistently. This removes the need to
reason about whether a component or one of its descendants may suspend now or
after a future refactor.
